# 任务流水线 — 规则与操作规程

**建立日期**：2026-08-11
**数据目录**：`tasks/`（看板数据、配置、生成的看板页面）
**工具入口**：`npm run board -- <命令>`（零依赖，Node 20+）
**看板页面**：`tasks/workbench.html`（生成产物，浏览器直接打开）

---

## 模型（用户定义的三段流程 → 七个阶段）

```
① 想法输入与判断        ② 任务调度与拆解              ③ 开发与交付
┌──────────┐      ┌──────────────┐      ┌─────────────────────┐
│ 想法收件箱 │ →判断→ │ 待办 → 已拆解 │ →调度→ │ 开发中 → 测试中 → 上线中 → 完成 │
└──────────┘      └──────────────┘      └─────────────────────┘
     ↘ 冷藏 / 已否决（理由留档）
```

- **想法输入**：用户在对话里随口说（短视频、灵感、别人的产品），CEO 会话跑
  `board idea` 收进收件箱——**说了就算收到，不需要用户填任何表**。
- **判断**：CEO 按四条标准（见 `tasks/config.json` 的 judgment）给结论：
  立项（必须写出验收标准）／冷藏（好想法但不是现在）／否决（理由留档）。
  **写不出验收标准的想法不允许立项**——这是防止看板变成愿望清单的唯一闸门。
- **调度与拆解**：`board next` 是唯一的调度算法——**完成优先于开工**（拉动式）：
  上线中 > 测试中 > 开发中 > 已拆解 > 待办拆解。有未完成子卡的父卡是容器，调度永远指向子卡。
- **开发与交付**：dev/test 各有 WIP 上限 2，满了就不许再开工；完成必须带产出物证据
  （commit hash / 文件路径 / 链接），否决必须带理由——**空口无凭的流转会被 check 拦下**。

4. **收工必写日报** `docs/YYYYMMDD-worklog.md`（见下）
5. 收工 commit（本地即真相，push 只作备份，不是完成条件）

### ⛔ 收工必写日报（20260816 起）

用户当天的原话是「怎么没看到你努力」。查下来产出**全部**落在 `board.json` 的卡片历史
和 commit message 里 —— 要看进度得去 diff JSON。**工作可见性是执行者自己的责任，
不能要求老板去读数据文件。**

每个周期收工写一份 `docs/YYYYMMDD-worklog.md`，至少包含四段：

| 段 | 内容 | 为什么必须有 |
|---|---|---|
| 今天做了什么 | 结论 + commit hash + 实测数字 | 没有 hash 的完成等于没完成 |
| **明确没做、以及为什么** | 主动放弃的、留到下一轮的 | 只报喜的日报是假的；「没做什么」往往比「做了什么」更值钱 |
| 公司状态 | 当天读到的现金/看板数 | 强制每天真的去读一次账 |
| 下一轮从这里开始 | 具体到第一个动作 | 下个周期不从「我记得上次做到哪」开始 |

同一天跑第二轮就追加到当天那份，不新建文件。

用户要做的只剩三件事：**说想法、解锁阻塞、对外动作**（付款/授权/见客户）。

## 分工与编制（2026-08-16 起）

### 编制原则：按钱设计，不按职能设计

**每个岗位必须能回答「我的产出离钱多远」。** 回答不了的岗位不设。

起因：2026-08-16 盘点发现公司 44 张卡在推、15 个 commit 在 5 天里，而收入 $0、付费客户 0。
执行力一直在，缺的是执行力对准了钱。**这种情况下无脑扩编，只会用更快的速度做出同样的 $0。**

### 花名册

岗位说明书在 `.claude/agents/*.md`，**会话启动时自动注册**，可用 `subagent_type` 直接调用。
⚠️ 新增岗位当轮不生效，要么重开会话，要么让 agent 自己先 `Read` 那份说明书。

| 岗位 | 文件 | 目标 | 硬边界 |
|---|---|---|---|
| **CEO** | 主会话 | 判断、排产、协调、对用户负责 | 不代替用户做对外动作 |
| **收款官** | `revenue-officer.md` | 把**已有客户**身上该收而没收的钱收上来 | 绝不代发任何对外沟通 |
| **交付工程师** | `delivery-engineer.md` | 做完已签约的活，解除收款前置 | 不碰生产、不做对外动作 |
| **财务官** | `finance-officer.md` | 让公司随时知道还剩多少钱、下一笔何时进 | 绝不执行真实收付款 |
| **质检官** | `auditor.md` | 验证「说完成了」是不是真完成 | 只判断，不修 |
| **资产分析师** | `asset-analyst.md` | 盘家底、估变现路径、核实「我们已经有 X」的说法 | 只读，不推测性填空 |
| **合规审查员** | `compliance-officer.md` | 对外资产不踩红线 | 只读排查，不下线服务 |
| 想法源 | **用户** | 说想法、解锁阻塞、**一切对外动作** | — |

### 共同铁律（写进每一份岗位说明书）

1. **每个结论必须指回 `文件:行号` 或 commit hash。找不到证据就写「无证据」，禁止推测性填空。**
   —— 编造的乐观比诚实的坏消息危险得多。今天最重要的三个发现全部来自「转述与事实不符」。
2. **一切对外动作过用户。** 不发邮件、不联系客户、不部署生产、不碰客户资产。
3. **同一个问题连续 2 次没解决 → 停下来报告**，不要第 3 次。
4. **`git add` 只加自己改的文件。** 仓库里常有别的会话的未提交改动。

### 派活规则

- CEO 每轮从 `board next` 取事，判断归谁，dispatch；**一个 agent 一次只做一个可交付单元**
- 交接物是**文件与 commit**，不是对话——对话会被压缩掉，文件不会
- 声称完成且会被用来对客承诺的，**由质检官复核后 CEO 才签字**（施工与验收不能是同一个人）

## 硬停止条件（对定时会话同样生效）

- 同一个问题连续 2 次没修好 —— ⛔ 停，把卡 `--block` 写清卡在哪
- 需要外部账号 / API Key / 付款 —— ⛔ 绝不猜测，`--block` 等用户
- **不做任何对外动作**：不发邮件、不发消息、不碰客户资产、不对外发布——对外永远过用户
- `board check` 报错且一次没修好 —— ⛔ 停下来留言，不要修第二次

## 不变量（check 守着的）

唯一 id ／ 阶段与流转合法（按 config 流转表）／ 立项卡必有验收标准 ／ 完成卡必有证据 ／
否决卡必有理由 ／ 父卡不能先于子卡完成 ／ dev、test WIP ≤ 2 ／ 每张卡有完整历史
