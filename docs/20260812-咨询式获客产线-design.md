## 一、这条产线要解决什么

现在这个市场里，同行的打法只有两种：报价，和说自己技术好。没有人在客户付钱之前分析客户的生意。

差异化不在「分析得更细」，在两件事：

1. **诊断先白送。** 对方一分钱没付，就已经看到自己生意的问题被说中了。
   模板店和接单个人不是不会，是售前不敢投入这个成本 —— 我们的成本是 AI 时间。
2. **分析决定卖什么，不只是怎么卖。** 同行只能卖网站（一锤子 299–499）。
   我们识别出这家健身房真正缺的是在线约课，那就是预约系统 —— 客单价高一档，且能收月费。
   **同一条线索，别人卖 500，我们卖 5000 + 月费。** 差异不在话术，在识别出了不同的生意。

看板对 `c-92fce4` 的判定理由写的是：不做这个就退化成 299/499 模板店。这份设计是那张卡的落地。

### 已有的实证

README「评分口径」一节记录过一次实测，是这套逻辑的雏形：

同一条评论「我也想搭建一个网站」——
- 不给模型看昵称：65 分 /「其他」/ 标「信息不足」
- 给了昵称 `Bing Fitness`：72 分 /「预约系统」/ demo 建议落到「周课表 + 在线约课两步完成」

**一个昵称就能让判断翻盘。一个主页能翻多少，就是这条产线的赌注。**

## 三、目标管线

```
opencli xiaohongshu search "<同行推广词>"     → 同行笔记 + url(带 token)
        ↓
opencli xiaohongshu comments <note-url>      → 评论 + userId + profileUrl + IP属地
        ↓
   L1 粗筛（现有 analyzer 改口径，便宜，全量跑）
        ↓  地域过滤（非北美直接丢）+ 这个人值不值得点开主页
opencli xiaohongshu user <userId>            → 最近 N 篇笔记标题
        ↓
   L2 生意诊断（新，src/diagnose.js）
        ↓  行业 · 生意规模 · 现有线上资产 · 真正瓶颈 · 推荐产品
   诊断书 HTML（一页，挂在品牌域名下，可发链接）
        ↓
   私信草稿  ——  本人点发送
```

### 为什么必须分两级

不能对每条评论都去拉主页。主页访问是**新增的高频动作**，是这条链路里风控上最贵的一步。

- **L1** 吃评论文本 + 昵称 + IP 属地，判断「值不值得深挖」。便宜，全量跑。
- **L2** 才花主页访问预算。每轮最多 8 个主页。

把这两级合成一级，等于拿账号赌一个本来在 L1 就能免费筛掉的判断 ——
实测里那些广东 / 北京 / 陕西 IP 的评论者，一次主页访问都不该花。

### 评分口径要跟着换

现在 prompt 问的是「这个人是否明确在找人做网站」。**在同行推广帖底下，这个问法是错的** ——
能在那儿留言的，意向已经默认存在了。该问的是：**他是什么生意，他的生意缺什么。**

这是「分析需求而不是报价」落到代码里的那一行。

## 四、已定的三个决策

### 1. demo 形态：先诊断书，回了再做站

| 阶段 | 产出 | 成本 | 触发条件 |
|---|---|---|---|
| 第一步 | 一页生意诊断（HTML，发链接） | ~10 分钟/条 | L2 通过 |
| 第二步 | 可点的行业样板（2 页，带对方店名/真图） | 1–2 小时/条 | **对方回复了才做** |

不回复就不投入做站，是产线量能铺开的前提。

诊断书的结构（四段，不多不少）：

```
你的生意    Bing Fitness · 私教工作室 · 多伦多
我看到的    IG 有 3k 粉但没有落点；约课靠 DM 手动排
真正的瓶颈   不是没网站，是排课占掉你每天 1 小时
建议方案    预约系统 > 官网
```

「真正的瓶颈」那一行必须**和对方自己以为的需求不同**，否则这份诊断没有存在价值 ——
他自己就知道他没网站，不需要我们告诉他。

### 2. 交付菜单：四条全开，CRM/ERP 单独排队

| 产品线 | 48h 产线 | 说明 |
|---|---|---|
| 官网 / 展示站 | ✅ | 现有能力，一锤子买卖，但是最好的入口 |
| 预约 / 排课系统 | ✅ | 健身、美业、诊所、教育、上门服务。客单价高一档，能收月费 |
| 会员 / 积分 / 优惠券 | ✅ | 餐饮、零售、美业回头客生意。比预约多一层交易/余额逻辑 |
| CRM / ERP / 定制系统 | ⛔ 标「重线索」 | 客单价最高，但要对接对方现有流程，48h 出不了 demo。走人工路线，不进 48h 产线 |

`DEMO_TRACKS` 相应重构：从「十个站型」改成「四个产品线 × 行业」两维。
模型选产品线（枚举，可聚合成看板），行业自由填（长尾，聚合不了也没必要）。

### 3. 诊断书托管：挂在品牌域名下

`https://idearise.ca/d/<slug>` —— 对方点开看到的是一家真公司，顺手能点到案例页和关于我们。

发一个 Cloud Run 默认域名给陌生人，观感接近钓鱼链接。这一步的转化率差异比页面本身的设计更大。

代价：要改 idearise 项目，**跨仓库**。本仓库负责生成诊断书 HTML，
idearise 负责提供 `/d/<slug>` 这个公开路由。两边的接口是一个静态文件目录，不是 API。

## 五、抓取层换成 opencli（2026-08-12 已实测）

项目 CLAUDE.md 写死：**所有联网抓取优先走 opencli，小红书强制走 opencli**。
现有 `src/scraper.js` 走的 CDP Proxy 是该规则里的**回退路径** —— 而实测证明不需要回退。

`opencli v1.8.6`，daemon + 扩展均 connected。四条只读命令实跑结果：

| 命令 | 结果 | 对本设计的影响 |
|---|---|---|
| `search "帮客户做网站" --limit 5` | ✅ 返回 5 条，全是同行推广帖 | **商业假设成立**：搜同行推广词能直接捞到竞争对手 |
| `comments <note-url> --limit 8` | ✅ 每条含 `userId` + `profileUrl` | **「点头像」入口现成**，不用自己实现 |
| `comments` 的 `time` 字段 | ✅ 形如 `03-02美国` / `02-28广东` | **IP 属地在 L1 就拿到了**，见下 |
| `user <uid> --limit 6` | ⚠️ 只返回笔记列表 | 缺简介 / 粉丝数 / IP 属地，见下 |

### xsec_token 的坑整个消失了

README 记录的三个设计决定里，「为什么不用 puppeteer / playwright」那一节的核心论据是
xsec_token 和登录态。opencli 的适配器把这两样都兜住了：`search` 返回的 `url` 和 `author_url`
本身就带 token，`comments` 直接吃完整 note URL。

**原计划里「开发前必须先验的地基假设」不复存在** —— 不需要在详情页里模拟点击头像，
`profileUrl` 是搜索结果的一个字段。

### 意外收获：IP 属地不用抓主页

`comments` 的 `time` 字段自带属地。这比预期值钱得多：

北美客户是目标市场，而地域过滤现在可以放在**最便宜的 L1 层**完成 ——
广东/北京/陕西的评论者在花掉任何主页访问预算之前就被筛掉，
L2 的 8 次主页配额全部花在美国/加拿大 IP 的人身上。

### 缺口：`user` 不返回简介 / 粉丝数

实测返回字段只有 `id / title / type / likes / cover / url`。

**但这个缺口比想象中小。** 实测样本 `66deb3cc000000001d03347c`：

- 昵称「造梦设计师01」—— 只看昵称，L1 大概率判成设计 / 建站相关从业者
- 6 篇笔记标题全是追星内容（方逸伦、柳眼、雪天浪漫）—— **粉丝号，根本不是生意**

**昵称会骗人，笔记标题不会。** README 里 `Bing Fitness` 那条实测证明昵称能让判断变好，
这条证明昵称也能让判断变坏 —— 两边指向同一个结论：必须看主页，而笔记标题就够了。
简介和粉丝数是锦上添花，不为它们回退到 CDP。

### 缺口：L2 会扑空

实测 `5b221224f7e8b904b20543e2` 返回 `EMPTY_RESULT`：该用户没有公开笔记（销号 / 私密 / 全删）。

**这是常态不是异常。** 处理方式：
- 扑空的记 `profiles.status = 'empty'`，不重试（重试改变不了对方的隐私设置）
- 降级到「昵称 + 评论原文 + IP 属地」做诊断，但**分数封顶**，不进第一步诊断书
- 扑空率要统计。若长期超过 50%，`MAX_PROFILES_PER_RUN` 的实际有效产出腰斩，排产要重算

## 六、数据模型

沿用现有 `leads` / `analysis` 分表的理由：生命周期不同，换 prompt 想重跑，
`DELETE FROM diagnoses` 就能重来，不用重付一次抓取的风控成本。

新增两张表：

```sql
CREATE TABLE profiles (
  user_id       TEXT PRIMARY KEY,      -- opencli comments.userId
  nickname      TEXT,                  -- opencli comments.author
  recent_notes  TEXT,                  -- JSON 数组：opencli user 的 title + likes
  profile_url   TEXT,                  -- opencli comments.profileUrl
  status        TEXT NOT NULL,         -- ok | empty（无公开笔记，见第五节）
  fetched_at    TEXT NOT NULL
);
-- 无 bio / followers 列：opencli user 不返回，且实测证明笔记标题已足够判断行业。
-- ip_location 不在这张表：它来自 comments.time，属于 leads 而不是 profile。

CREATE TABLE diagnoses (
  lead_id       INTEGER PRIMARY KEY REFERENCES leads(id) ON DELETE CASCADE,
  user_id       TEXT REFERENCES profiles(user_id),
  industry      TEXT,                  -- 自由填，长尾
  business_size TEXT,                  -- 个人 / 单店 / 多店 / 公司
  online_assets TEXT,                  -- 现有线上资产：有无官网、IG、Google Business
  bottleneck    TEXT,                  -- 真正的瓶颈（≠ 他自己以为的需求）
  product_line  TEXT,                  -- 枚举：官网 / 预约 / 会员 / 重线索
  is_heavy      INTEGER DEFAULT 0,     -- CRM/ERP 类，不走 48h 产线
  diag_html     TEXT,                  -- 诊断书正文
  diag_slug     TEXT UNIQUE,           -- /d/<slug>
  dm_draft      TEXT,                  -- 私信草稿，永不代发
  model         TEXT,
  diagnosed_at  TEXT NOT NULL
);
```

`leads` 表加两列：`author_user_id`（连到 profiles）和 `ip_location`（来自 `comments.time`，L1 地域过滤用）。

## 七、风控预算

走 opencli 后，浏览器节奏由适配器管理，我们不再自己控制点击与翻页。
但**命令调用频率仍然是我们的责任** —— 保留保守节奏，理由和 README 里那条一样：
硬撑是把账号推向封禁的最快方式，而这个账号是本人日常在用的那个。

| 参数 | 默认 | 理由 |
|---|---|---|
| `MAX_KEYWORDS_PER_RUN` | 5 | 沿用现值 |
| `DELAY_BETWEEN_CALLS` | 20–45 秒 | opencli 每次调用之间 |
| `MAX_PROFILES_PER_RUN` | 8 | L2 的硬上限 |
| L1 进 L2 的阈值 | 北美 IP **且** score ≥ 50 | 两个条件都要满足，这是预算的实际闸门 |

**地域过滤放在 score 之前判断** —— 它免费（`comments.time` 已经在手里），
而 score 要花一次 AI 调用。先做免费的那个。

opencli 返回 `AUTH_REQUIRED` 或明显的风控错误时：**立刻停整轮，不重试、不换词硬撑。**
`EMPTY_RESULT` 是正常业务情况（用户无公开笔记），不算风控信号，记录后继续。

## 八、合规边界（不可协商）

小红书 2026-03-10《关于打击AI托管运营账号的治理公告》禁止利用技术手段模拟真人、
进行非真实内容创作或虚假互动；2026-06-10《关于规范搜索及问答生态相关行为的公告》
进一步禁止通过评论区配合、账号矩阵联动等方式人为制造口碑。处置为降权、下架、封禁。

本产线做的是**不模拟真人的那部分**：读、判断、写草稿。

- ⛔ 不代发私信，不代发评论。最后一下由本人点发送。
- ⛔ 不伪装成普通用户，不假装自己也遇到同样问题，不承诺结果，不报价。
- ⛔ **不在同行笔记下留评论。** 见下一节。

## 九、两个商业风险

### 1. 在同行帖下捞人，是挖墙脚

同行会看到评论区的动静。策略上因此定死：**只读评论区、只私信，绝不在同行笔记下留任何评论。**
留评论既是挖墙脚的明证，也正好撞在上述公告的「评论区配合」条款上 —— 两个理由指向同一个禁令。

### 2. 真正的吞吐瓶颈是私信，不是抓取

小红书对陌生人私信有条数限制且容易限流。产线做到每天能产出 20 份诊断，
不等于每天能发 20 条私信。**排产要按私信配额倒推，不是按抓取能力。**

这一条会直接决定 `MAX_PROFILES_PER_RUN` 的实际取值 —— 生产比发货快没有意义。
首轮跑完要实测本人账号一天能安全发多少条，再回来校准这个数字。

## 十一、不做什么

- **不做自动发送。** 任何形式，任何借口。
- **不做多平台。** 只有小红书。加平台是新写一个 scraper 的事，与本设计正交。
- **不做 CRM/ERP 的自动 demo。** 标成重线索，走人工。
- **不做第二步样板站的自动化。** 先手工做几个，摸清哪些部分真能复用，再谈骨架。
  过早抽象一个还没做过三次的东西，抽出来的一定是错的。
- **不翻页。** README 已写明：翻页是触发风控的高危动作。
- **不为了补 bio / 粉丝数回退 CDP。** 实测已证明笔记标题足够判断行业，
  为两个锦上添花的字段重新引入一套自己维护的 DOM 选择器不划算。
