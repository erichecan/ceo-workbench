## 2026-09-27 · 新增公开预约页面 `/book/[slug]`

**这次改动想达成什么**：给还没签约的新客户（美甲/美容等）看 demo、促成交用——不用注册登录，客户打开
`/book/<店铺slug>` 就能看到这家店的服务项目并提交预约请求。换一个店的 demo 只需要在数据库里加一条
Workspace + Service 记录（换店名/logo/服务项），不用改代码。

**技术观测**（我负责，见下）：
- GitHub Actions `deploy-booking-portal.yml` 跑绿：https://github.com/erichecan/ceo-workbench/actions/runs/36292824276
- 生产库手动加了 `Workspace.logoUrl` 字段（精确 ALTER TABLE，避开 db push 漂移风险，见任务台账
  `docs/20260913-预约系统迁移archive-beauty-tasks.md` 2026-09-27 条目）
- 部署后独立验证（不是只信 workflow 自带的 verify 步骤）：
  - `/book/lead-99`（真实客户 Shine Nail Studio）→ 200
  - `/book/不存在的slug` → 404
  - `/login` → 200，`/calendar`（未登录）→ 307，老功能未受影响
- `code-review high` + `security-review` 跑过，无高/中置信度问题；时区换算用 EDT/EST/Dublin 三组夏令时
  边界案例验证过

**定性观测**（Eric/客户负责，具体问一句什么、问谁）：

  打开是空列表，这是预期状态，不是 bug）。下一步是给某个目标行业（美甲/美容/私教）配一条真实 Workspace +
  几个 Service 记录，然后拿这个链接去问一个具体的目标客户："这个预约页面像不像给你店做的、你愿不愿意
  在这上面填一次预约看看" —— 这句话还没问出去，不能算这个功能已经产生获客效果

## 2026-09-27 · 预约页交互打磨 + 日历标记线上预约来源

**这次改动想达成什么**：Eric 反馈"能看懂功能但交互体验不够好，提交慢，店主找不到预约在哪查看"。用
taste-skill（`leonxlnx/taste-skill`）审视后确认两处真问题并修复：选中态/禁用态无反馈、顾客线上提交
的预约在日历上和店主手动录入的长得一模一样、店主没有任何入口知道"有新预约"。

**技术观测**（我负责，见下）：
- GitHub Actions 跑绿：https://github.com/erichecan/ceo-workbench/actions/runs/36318779264
- 部署后独立验证：`/book/lead-99` → 200；未登录访问 `/api/appointments/pending-count`（新增端点）→ 307
  重定向到 `/login`，和既有 `/api/appointments` 未登录行为一致，鉴权没有被破坏
- `npx tsc --noEmit` + `npm run build` 本地跑过，无错误
- 本地用 chrome-devtools 实测过一遍新交互：选中服务出现勾选高亮、缺字段时按钮下方实时显示"还差：X、Y"
  （随填写实时收窄），符合预期
- 提交慢的根因已定位（不是本次代码引入的问题）：`/book/lead-99` 实测冷启动 3.9s、热启动 0.7-0.9s，
  来自 Cloud Run `min-instances=0` + `asia-east1` 与目标客户（多伦多）跨太平洋延迟。Eric 明确要求demo
  阶段先接受，等真实客户 demo 时再评估是否值得迁移区域（需要新建 GCP 权限之外的 Artifact Registry 仓库）

**定性观测**（Eric/客户负责，具体问一句什么、问谁）：
- 这几处改动本身是店主体验层面的修复，不直接影响"是否获客"，不需要单独去问客户；仍然卡在同一件事上：
  还没有对某个真实目标客户问出"这个预约页面像不像给你店做的、你愿不愿意在这上面填一次预约看看"
- 状态：**已达成**（技术层面：交互反馈 + 线上预约可见性问题已修复并验证）；获客效果观测状态不变，仍是
  上一条记录里说的"待观测"
