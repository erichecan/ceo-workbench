### 工单说的 vs 实际是什么

工单 X10 写的是「管理员重置密码这条路绕过强密码策略」——听上去是漏接了一个校验函数。
查下去发现根因宽得多：

> **`withAuth` 是纯验签 + permVersion 比对，全程不查 `isActive`。**
> `isActive` 只在 `app/api/auth/login/route.ts` 登录那一刻校验一次，而 token 有效期 **7 天**。

推论：一切「改了账号凭据或状态」的动作，如果只写数据库字段而不 `permVersion + 1`，
**都没有把人真正踢下线**。最刺眼的一条 —— 员工离职当天在系统里停用，第二天照样能下单。

### 修的五处

| 接口 | 原来 | 现在 |
|---|---|---|
| `PUT /api/users/[id]` 管理员改密 | 只看 `length >= 6` | 走 `assessNewPassword`（比对被改人的邮箱/姓名，不是操作者）+ `permVersion+1` |
| `POST /api/users` 建号初始密码 | 只看 `length >= 6` | 同一个校验 —— 生产上那 42 个 `test123` 就是从这条唯一还开着的口进来的 |
| `POST /api/users/[id]/reset-password` | 不作废 token | `permVersion+1` |
| `DELETE /api/users/[id]` 停用 | 只写 `isActive=false` | `permVersion+1` |
| `POST /api/gdpr/delete` 匿名化 | 只写 `isActive=false` | `permVersion+1` ——「删了还能继续访问」直接违背 GDPR Art.17 |

### 顺带撞出来的两个用户可见 bug

1. **两个导航栏的「修改密码」是死的**。`components/classic/OdooNav.tsx` 和
   `components/shared/nav.tsx` 发的字段是 `oldPassword`，而接口 destructure 的是
   `currentPassword` → 永远 `undefined` → **100% 报「请填写当前密码与新密码」**。
   只有强制改密页 `/change-password` 发对了字段，所以这个洞一直没被发现。
2. **前端四处还写着「至少 6 位」**，后端 `PASSWORD_MIN_LENGTH = 10` 且带黑名单。
   用户照提示填 6 位，前端放行、后端打回。已改为前后端共用 `assessNewPassword`。
